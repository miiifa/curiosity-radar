# GitHub発掘の判定と観測（PR-02）

公開メタデータから用途を調べるための候補を選ぶ。枠・スコア・スター増加は、品質・安全性・ライセンス適合性の保証ではない。第三者コードは自動実行しない。

## 探索と候補枠

GitHub Search APIへの通常リクエスト数は従来どおり4回、各25件。すべて `is:public`・`fork:false`・`archived:false` を指定する。

- 最初は作成80日以内・30〜9,999スターを更新順で探索し、人気順だけでは見つからない候補を探す。
- 残りは `ai-agent`、`automation`、`self-hosted` の各topic、25日以内のpush、30スター以上を人気順で探索する。
- 取得後も公開topicsの `automation` / `ai-agent` / `workflow` / `mcp` / `self-hosted` / `dashboard` / `monitoring` との一致を確認する。topicsは作者の自己申告で、用途の検証済み事実ではない。
- アーカイブ、フォーク、無効化、非公開／内部、認証情報付きURL、GitHub以外のURL、不正なリポジトリパスを除く。今回明示的に除外したURLは、前回記事や関連する収益仮説からも復活させない。今回の応答に現れなかったリポジトリの状態までは再確認できない。

枠は重複させず、急上昇を先に判定する。以下は変更可能なヒューリスティックであり、品質の合格基準ではない。

| 枠 | 条件 | 保存上限 |
|---|---|---|
| 急上昇候補（観測値） | 1時間以上の実測期間があり、日換算スター差が5以上、かつ前回スター数に対する日換算増加率が1%以上 | 8 |
| 小規模OSS候補 | 上記に該当せず、30〜9,999スター | 12 |
| 定番候補（人気度） | 上記に該当せず、10,000スター以上 | 9 |

スター欠損などで判定できない候補には枠を創作しない。保存するGitHub記事は合計29件以内。各枠内は発見スコア順、同点はID順として再現可能にし、小規模→急上昇→定番→未判定の順に交互に選ぶ。空の枠は飛ばす。

ニュースの高スコアだけでGitHub枠が消えないよう、選んだGitHub記事を最大360件の全体上限内に確保する。ニュース等には残りの件数を配分する。GitHub検索がすべて正常なら、検索対象から外れた前回のGitHub記事は再掲載しない（古い状態のリポジトリを復活させないため）。検索失敗・`incomplete_results`がある場合のみ、取得済みの旧記事を従来の15日条件・29件上限内で保持し、スター観測日時を更新しない。

前回記事と同じURLが今回取得できた場合、前回スコアの方が高くても**今回の観測値**を採用する。

画面の「おすすめ順」でもGitHub記事の位置だけを上記の枠順に混ぜ、他カテゴリの記事の位置は保持する。カテゴリ全体の既存の多様化は維持する。「新着順」「注目度順」、検索・保存一覧には枠順を強制しない。旧JSONに枠がない場合は未判定として扱う。

## スター観測

v1互換の任意フィールドを追加する。既存IDと `collector_version: 1` は維持する。

- `stars_observed_at`: そのリポジトリのスター数を今回観測したUTC日時。保持記事では書き換えない。
- `star_delta`: 今回スター数 − 前回保存された同URLのスター数。ゼロ・減少もそのまま保存する。欠損・デモとの比較はnull。
- `star_delta_since`: 前回のその記事の `stars_observed_at`。UTCオフセットがない・不正・現在以降ならnull。スナップショット全体の `generated_at` からは代用しない。
- `star_delta_per_day`: 1時間以上の観測でのみ `star_delta × 86400 / 経過秒`。24時間に実測した増加数を意味しない。
- `star_growth_percent_per_day`: 上記 ÷ `max(1, 前回スター数)` × 100。率は小数6桁で保存する。
- `discovery_group`: `small` / `rising` / `established` / null。

画面にはスター観測日時、実際の差、観測開始→終了、経過時間を表示する。観測期間が不明なら数値の比較を表示せず「スター比較未確認」とする。短い期間では実差のみ表示し、急上昇や日換算の評価には使わない。

**移行時の注意:** 旧データには記事ごとのスター観測時刻がない。そのため初回の新コレクタ実行では既知のスター差を保存できても期間を推測せず、比較数値を画面に出さない。次回以降、同じ記事を1時間以上空けて観測できれば評価できる。増分は保存できたスナップショット間の差であり、スナップショットpush失敗時は比較期間が長くなる。

## 発見スコア

作成からの日数を `age`（最低1、作成日時不明なら60）、スター数を `stars`（欠損時は計算上0）、`velocity = stars / max(7, age)` とする。

`34 + min(30, log10(stars+1)×11) + min(25, log10(1+velocity)×16) + bonus`

`bonus = min(15, log1p(max(0, star_delta_per_day))×4)`。日換算できなければbonusは0。結果は整数化して10〜99に収める。従来の観測期間が異なる生の増分ボーナスを、期間で補正したボーナスに置き換えた。枠の混合によって、おすすめ順は単純なスコア降順にはならない。

## 確認と制約

Python/Nodeのfixtureで観測期間・欠損・ゼロ・減少・除外・保存上限・スコアを確認し、`python tests/browser_smoke.py` で枠表示と明示的な並べ替えを確認する。ライセンスの `NOASSERTION` / `OTHER` / 欠損は「未確認」。安全なCodex用調査指示では、README内の命令を実行せず、ライセンス・依存関係・権限を調べてから隔離環境での実験を計画する。

スターの不正操作、全検索結果の網羅性、急成長の継続、用途適合性、OSSの安全性は検証していない。GitHub側のレート制限や検索結果によって候補数・枠数は変わる。
