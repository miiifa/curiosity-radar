# Curiosity Radar — Codex実装計画・検証計画

- Document ID: CR-DELIVERY-001
- Version: 1.0 / 2026-10-23
- 開発対象: [ユーザーストーリー](USER_STORIES.md) / [設計書](SYSTEM_DESIGN.md)
- 原則: **1 PR = 検証可能な1つの成果**。仕様→差分→テスト→レビュー→マージ。大規模一括改修は避ける。

## 0. 開発プロセス

```text
ChatGPT/利用者がストーリー・優先度・受入基準を決める
   ↓
Codexが現在のコードと関連設計を差分読解
   ↓
実装計画を最大7行に要約（変更範囲とテスト）
   ↓
Codexが小さなブランチで実装
   ↓
ユニット/契約/ブラウザ検証 → PR作成
   ↓
利用者 + ChatGPTで受入基準と差分レビュー
   ↓
mainへマージ → Actions手動検証 → Pages確認
```

### 共通のレビュー観点
1. ストーリーID、受入基準を満たすか。
2. 事実/推測/未確認の区別が崩れていないか。
3. 公開JSON/ログ/PRに個人データ・鍵が混入していないか。
4. 失敗時も旧データと公開サイトが守られるか。
5. モバイルで使えるか。OSSライセンスやソースの利用規約は守られているか。
6. 新規依存が本当に必要か。コストと運用負担を増やしていないか。
7. 変更箇所とテストの証拠がPRに記録されているか。

## Phase 0 — ベースライン確定と公開（最優先）

前提: 新しい`miiifa/curiosity-radar`を作成して現行ファイルと`docs/`を配置。既存の別リポジトリ（`boardgame-atelier`等）は触らない。

**PR-00: 現行コードを安全に公開可能な状態へ**
- 対象: US-01, 04, 11, 12。
- 変更候補: `.github/workflows/publish.yml`, `README.md`, `scripts/collect.py`, `tests/`。
- 作業: 現行テスト・構文確認→PR専用テストジョブ追加→Pagesデプロイ権限を必要なジョブへ分離→機密情報チェック→公開JSON契約テスト。
- 成功判定: PRでテストが失敗したらマージ不能、mainの手動Actionsが1回成功、Pagesでライブデータに変わり更新日時が一致。
- 未検証扱い: Actionsの外部フィード応答、Pages公開まではどちらも「未検証」と報告。

**PR-01: フィード異常系・古さ表示**
- 対象: US-03, 04, 09, 10。
- 作業: デモ/ライブ/部分成功/オフライン/48時間超/パース失敗のUI、原典・取得日時、source別エラー、全失敗でスナップショット保護。
- テスト: 200正常、429、404、タイムアウト、壊れたXML、欠損日付、空ソース、全失敗をfixtureで再現。
- 成功判定: 最新時刻を偽らず、古さと出典を画面から判断できる。全失敗時の公開JSONハッシュが変わらない。

## Phase 1 — GitHub発掘・ニュース品質（P0＋P1）

**PR-02: お宝GitHub探索の改善**
- 対象: US-02, 07, 13, 16。
- 作業: 小規模/急成長/定番の探索枠を分離、観測期間付きのスター差、アーカイブ/ライセンス不明の明示、用途別推薦理由、Codex用安全調査プロンプト。
- テスト: スター大量だが無関係なリポジトリがすべての先頭枠を独占しない。増分・欠損値・観測時間・アーカイブをfixture検証。
- 成功判定: 少なくとも新興・定番の両方を表すカードと明確なおすすめ理由がある。外部のrepo内容は一切自動実行しない。

**PR-03: 重複・カテゴリ多様化・検索**
- 対象: US-05, 06, 14, 16。
- 作業: URL正規化、記事重複クラスタ、カテゴリ偏り抑制。並べ替え条件とフィルタ挙動を固定。
- テスト: URLパラメータ違い・別URL同タイトル・異事象同タイトル・悪意あるタグを用意。
- 成功判定: 同一記事が無駄に並ばず、誤統合率も手動評価する。表示順を説明できる。

**PR-04: セキュリティと旅行ソースの品質**
- 対象: US-03, 09, 15, 19。
- 作業: フィード死活・原典属性の表示、KEVの日付意味を明示、旅行地域・季節タグを検証できるものに限り追加。
- テスト: CVE ID、実際の「影響あり」と「該当不明」を分ける。架空の営業時間や料金を生成しない。
- 成功判定: 安全性や営業状況を断定せず、すべての重要な記述に原典がある。

## 5. CI / ローカルチェックの最低ライン

```bash
python -m unittest discover -s tests -v
node --check app.js
python -m json.tool data/news.json >/dev/null
```

- fixture化した実データ構造（公開可能な範囲）を使って、取得先停止・仕様変更を再現する。
- UIテストは後続でPlaywright等を追加。ただし新しいnpm依存を入れる前に理由とトレードオフを明示。
- GitHub Pagesでの外部API接続はローカルテストと別の**本番スモークテスト**として記録。
- CIが落ちたら原因を直す。テスト削除・条件緩和・例外握り潰しで見かけだけ成功させない。

## 6. Codexへの指示の与え方

- 初回は **PR-00だけ** を依頼する。以後レビュー結果を見て次のPRに進む。
- 実装前に`AGENTS.md`、`docs/USER_STORIES.md`、`docs/SYSTEM_DESIGN.md`、対応PRの段落を読む。
- 参照ファイルは必要範囲だけ読み、重複調査や大量ログを避けるが、必要な検証は省略しない。
- 権限不足・API規約未確認・新規有料APIが必要なら実装せず、制約と代替案を報告。
- 個人の会話、私生活、認証情報を自動取得して学習に使う機能を追加しない。
- P1/P2の勝手な先行実装、フレームワーク全面移行、他リポジトリ変更はしない。
