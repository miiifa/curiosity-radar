# 新しいものを作るときの共通プレイブック

- Document: PROJECT_CREATION_PLAYBOOK
- Version: 1.0（2026-10-23）
- 用途: **新規アプリ・ツール・自動化・既存サービスの大幅改修**に再利用する。
- 注意: この文書をこのリポジトリに置いても、別のリポジトリやChatGPT/Codexの全会話に自動適用されるわけではない。毎回必要部分をコピーして指定する。

## 0. 目標と考え方

**目的は「コードを書くこと」ではなく「実際に役立つものを、安全に使い続けられる状態で届けること」。**

優先順位: 課題への適合・事実の正確さ > プライバシー/安全/利用規約 > ユーザー体験 > 保守性/検証可能性 > 運用費 > 開発速度 > 見栄え。
ただし、小さな試作品では複雑な設計を避け、素早く仮説を検証する。品質を落とすのではなく**検証範囲を目的に合わせる**。

## 1. 規模に応じて準備を変える

| 規模 | 例 | 開始に必要なもの | 完了条件 |
|---|---|---|---|
| S: 小さな修正 | 文言・軽微なUI修正・一つのバグ | 一文の目的と期待結果、関連テスト | 差分・直接関係するテスト・画面確認 |
| M: 新機能 | 新しいAPI接続、記事詳細、共有機能 | 1〜3件のユーザーストーリー、AC、変更範囲、失敗条件 | 自動テスト、手動確認、PRレビュー |
| L: 新製品/大規模変更 | 独自アプリ、認証・決済・大量の外部連携 | PROJECT_BRIEF、MVP境界、アーキテクチャ図、リスク、運用費、開発順 | システムテスト/運用確認、受入判断、公開・復旧手順 |

*AC = Acceptance Criteria（受入基準）。*
アイデアを話している段階でコードや大量のドキュメントを作る必要はない。**作ると決めた段階で、その規模に必要なものだけ作成**する。

## 2. 企画時の8項目（PROJECT_BRIEFの最小形）

1. **誰のどの問題か** — 誰が、いつ、何に困る/何を楽しみたいか。
2. **成功シナリオ** — ユーザーがどの画面で何をし、何が得られれば成功か。
3. **MVPで必須の3機能程度** — Must / Later / Not now に分ける。「全部欲しい」を初版の必須条件にしない。
4. **情報源・連携先・利用権限** — 正式API/公式データ/作成物、更新頻度、取得制限、引用・ライセンス、故障時の代替。
5. **データとセキュリティ** — 個人情報、外部への送信、公開範囲、認証、鍵、権限、悪用・誤判定リスク。
6. **技術選択** — UI、処理、データ、公開/実行先。既存技術を使えるなら利用。採用理由と**採用しない理由**を短く書く。
7. **費用・保守** — 月額上限、API課金、サーバー、依存先、障害通知、変更容易性。
8. **完成判定** — 正常例、例外例、端末/実環境テスト、評価者、公開後に観測する指標。

## 3. 役割分担

| 担当 | 主な責務 |
|---|---|
| 利用者（プロダクトオーナー） | 何を作るか、優先度、許容費用、公開、最終受入を決める |
| ChatGPT / Work | 要求の深掘り、一次情報や競合の調査、設計案・反論・トレードオフ比較、仕様化、レビュー。長い調査や複数サービス横断はWorkが向く |
| Codex | リポジトリの理解、実装、テスト、差分修正、PR、技術的問題の調査。要件外の機能は勝手に増やさない |
| GitHub | 真実の記録としてのIssue/PR/決定記録、履歴・自動テスト・配信 |

**境界は絶対ではない。** ChatGPTが実装・Codexが技術調査する場合もある。重要なのは「判断は要求と根拠に照らす」「実装はテストと差分で確認する」こと。

## 4. 開発フロー（1 PR = 1つの検証可能な成果）

1. **発見**: 会話で課題・利用体験・選択肢を検討。事実・推測・希望を分離。
2. **決定**: 最小のMVP/AC、出典・技術・公開先を確定。未決事項は明示。
3. **土台**: リポジトリのREADME、プロジェクトAGENTS.md、最低限のテストとCI、データ公開範囲を用意。Pages等の外部設定は最初に可否確認。
4. **細分化**: 「UI・収集・要約・公開を全部1回」ではなく、依存関係に従い小さいPRに分ける。
5. **Codex実装**: 変更するファイルとACを指定し、まず必要な関連箇所だけ読む。小さな差分で実装する。
6. **検証**: 静的/構文チェック、単体・結合、セキュリティ/URL入力検証、実機/本番スモークを分けて記録。
7. **レビューとマージ**: PRの差分、意図せぬ変更、仕様整合性、テスト、未確認、戻し方を確認してからmainへ。
8. **リリース後**: URL・データ更新・操作・障害時動作を実際に確認。使用経験に基づき優先度を調整。

### PRで必ず報告
- 何を変えたか / 変えていないか
- 対応した要求・AC
- 実行したテスト（成功/失敗）と未実行のもの
- 外部API・ブラウザー・本番環境で**確認できた事実**
- リスク、費用への影響、ロールバック
- 次にやるべき一つの小さな作業

## 5. 繰り返したくない失敗

- **コードを先に作りすぎない**: 情報源、免責、アクセス権、最重要体験を先に確認する。逆に仕様が不完全という理由でMVPを永久に止めない。
- **初日からmainへの連続直コミットを標準にしない**: 初期の土台構築は許容しても、通常はブランチ→CI→PR→レビュー→マージ。
- **設計書を増殖させない**: 最初はREADME + AGENTS + PROJECT_BRIEF/受入基準を中心に。詳細設計は必要になった時点で一つの正本に統合。v1/v2の併存には優先規則と整理期限をつける。
- **「CI成功」と「本番で正常」を混同しない**: データ内容、画面、スマホ・本番URL、更新の継続性は別チェック。
- **PR・mainの権限を分ける**: PRは原則読み取り＋テスト。本番反映ジョブだけ必要最小の書込み/配信権限。SecretをPRに公開しない。
- **自動化を過剰起動させない**: ドキュメント変更だけで高コストなニュース収集やAPI処理を回さない。収集と配信・テストのワークフロー分割を検討。
- **外部データの出所を偽らない**: 検索結果を公式情報、説明文をAI要約、仮説を実証結果、星の増分を未確認の24h増分と呼ばない。
- **公開リポジトリを個人データの保存先にしない**: API鍵、個人会話、住所・秘密、ブラウザーの履歴をコミットしない。

## 6. 実装の速さ・トークン効率
- プロジェクト開始時に既存ファイルを一度だけ概観し、その後は変更箇所と関連ドキュメントを優先して読む。
- 繰り返す調査結果はソース/取得日/決定理由をADR等に短く残す。情報が変わった可能性があるときだけ再確認する。
- チェックリストだけ満たす「形だけのテスト」は避ける。変更の危険度に合わせて検証の深さを変える。
- 長大な一括依頼ではなく、受入基準を伴う小さな実装単位にする。ただし意味のない微小PRへの分割はしない。
- 失敗を繰り返したらパッチを重ねず、失敗の発生条件・根本原因・回帰テスト・再発防止をセットで考える。

## 7. 完了定義（DoD）
- 実行・表示できるだけでなく、目的と受入基準を満たす。
- 入力不正・ネットワーク失敗・権限不足・データ欠落時の動作が確認できる。
- 主要な利用環境の動作確認（Android/PCなど）、アクセシビリティの最低限の確認。
- 誰でも再現できる起動・公開・復旧手順がある。
- テスト結果・デプロイ結果・実運用の確認が明確に区別されている。

## 8. 新しいプロジェクトを始める時の最初の依頼例

「このアイデアを個人開発したい。まず PROJECT_BRIEF を1ページにまとめ、代替案/リスクを比較し、MVPで必須の3機能、優先順位、受入基準、公開・費用・セキュリティを決めて。実装に入る前に不確定事項と検証計画を明示。合意した後にCodexへ渡す仕様と最初の1PRを作る。共通AGENTSルールに従い、必要以上の資料を作らない。」
