## 目的
誰もが見るニュースの大量配信ではなく、公式発表・開発者・本人の一次情報を掘り起こして、読む価値・試す価値・行動のきっかけを見つける。既存のGoogle News中心の収集はこのポリシーを満たしていないため改善対象。

## 情報源の階層
- A：行政・自治体・主催者・企業・公式開発チーム・被害企業自身の公表。
- B：GitHubの開発者のREADME/リリース、Qiitaの本人執筆記事、SNSの本人投稿、原著者の実験や検証。
- C：二次的なまとめ、転載、SEO・広告目的記事。原則として直接配信しない。原典を発見するための手掛かりとしてのみ扱い、原典が見つからない場合は掲載保留。
- 公式発表も「発信者がそう主張した」の確認であって内容の正しさの保証ではない。Qiitaの投稿はQiita運営の事実認定ではない。

## 六つのジャンルと収集・検証

| ジャンル | 一次情報の優先元 | 必ず確認すること |
|---|---|---|
| 旅行・イベント | 主催者、観光協会、自治体、交通・宿泊の公式告知 | 開催日・地域・申込期限・費用・アクセス・中止 |
| お得情報 | EC事業者、店舗、メーカー、交通事業者、国・自治体の制度 | 利用資格・対象地域・割引条件・上限・期限・実質額 |
| 技術・GitHub・AI・Qiita | GitHub Search/Release/README、モデル提供元の告知・ドキュメント、Qiita API v2作者記事 | 実際にできること、ライセンス、開発状況、試用費用、スター増分の期間 |
| セキュリティ | 被害企業の公式公表、IPA/JVN/JPCERT/CC/CISA、警察等 | 被害確定/調査中、漏洩種類、発生/公表日、利用者が取るべき対応、詐欺など二次被害 |
| 今流行りの話 | 原作者、公式コミュニティ、許可されたSNS公開情報、公開プロジェクトの伸長 | 話題の根拠と集計期間。Xの話題と表現するなら実際のXデータが必要 |
| 収益化のアイデア | 上記一次情報、実際の課金モデル/価格表、商用利用可能なOSS | 顧客課題、検証方法、競合、費用、規約、収益化仮説の未検証性 |

### 情報源候補
- GitHubの公式REST API、Release API、作者のREADME。
- Qiita公式API v2: https://qiita.com/api/v2/docs （2026-10-23調査時、非認証60回/時/IP、認証1000回/時。最新条件は実装時再確認）。
- 各AIモデル提供元の公式ブログ、モデルカード、変更履歴。
- 各自治体、観光協会、交通・イベント主催者の公式のRSSや許可されたAPI（利用規約とURLごとの動作を確認）。
- JVN / IPA / JPCERT/CC / CISA KEV、被害当事者の公表ページ。
- EC/店舗/交通の公式キャンペーン・行政支援の原典。
- Hacker Newsは話題発見の入口であって原著者・公式発信ではない。可能な限り原典へ辿る。
- Xの無許可スクレイピング/ログインRPAは採用しない。許諾されたAPI/埋め込みのみ検討。

## ソース管理と失敗時動作
- ソースごとに名前、所有者、カテゴリ、A/B/C、取得URL、方式、許諾/規約確認日、レート制限、最終成功時刻、エラーをレジストリ管理。
- 各アイテムに原典URL、発信者、公表日時、事象日時、終了/期限、最終更新、事実、公式の主張、解釈、未確認事項を分離。
- 統合重複排除はニュースの元事象単位。続報は関連づけ、訂正は履歴付き。
- 取得失敗時に古い記事を最新と呼ばない。部分障害と最終更新時刻を表示。
- 外部テキストは信頼しない。埋め込みスクリプトや指示文を実行せずHTMLを無害化し、本文の全文保存・再配布を避ける。

## 推薦の理念
情報ソースの信頼性と、個人にとっての面白さは別物。次の5軸の各1〜5点または「未評価」で推薦理由を見せる。
1. 発見度 2. 関連度 3. 行動しやすさ 4. 実利 5. 深く考察できる余地
数値の欠損は中間点で埋めない。スコアの計算と根拠を確認可能にする。セキュリティの緊急性は「おすすめ★」と分けて表示する。
関心外の意外な発見を15〜25%程度確保する案を試験し、定番OSSや特定メディアへの偏りを抑制する。

## 品質監査
初期評価は各ジャンルから5件程度を手動抽出して、原典・期限・数値の正確性、重複、広告誘導、面白さ、実践可能性を採点する。単なるクリック数では品質を判定しない。
現在の運用は1日2回の取得を基本とし、必要性・API規約・費用を検証するまで高頻度化しない。
