## 1. プロダクトの目的

### 一文で
「普段は知らなかった面白い技術・OSS・ニュース・旅行先・新しい活動を、自分に使える具体案とともに毎日発見する」個人用ニュース／発見エンジン。

### 想定ユーザーと利用場面
- 主なユーザー: Androidスマホ中心の個人。GitHubでの個人開発、AIエージェント、OSS活用、国内旅行、セキュリティ、ゲーム／ボードゲーム、面白いネットの話題に関心がある。
- 典型場面: 朝・夕に1〜5分で新しい発見を探す。気になるものを保存し、必要に応じてCodexに試作を依頼する。
- 見つけたいもの: 流行の大物だけでなく、まだ埋もれている実用的なリポジトリや、自分の生活／開発に転用できる題材。
- 機密の扱い: 個人的な会話履歴やプライバシー情報を公開GitHubリポジトリへ転記しない。初期興味カテゴリは一般化した公開可能な設定にする。

### 成功状態（目標値。実測・保証ではない）
- 毎日5分以内の閲覧で、1件以上「あとで試したい」「行ってみたい」と思える候補がある。
- クリックした記事は出典と元URLを確認できる。要約・推薦理由・収益仮説を事実と混同しない。
- 主要情報源の一時障害でも、フィードが突然空にならず、古い情報には警告が表示される。
- 直近7日で保存した候補のうち少なくとも1件を検証・試作に移せる（将来の利用評価目標）。

## 2. MVPの範囲

**MVP（初版の安定公開に必要）**
- GitHubリポジトリ発掘、AI、国内旅行、セキュリティ、ネットの話題、ゲーム・趣味、収益化仮説。
- 一般公開可能な情報源から定期収集、出典明示、重複除去、データ検証、鮮度表示。
- スマホ優先のカテゴリ・検索・並べ替え、保存・既読・好みの重みの端末内保存。
- 「なぜおすすめか」「30分で試すなら」「収益仮説をどう検証するか」を読み取れる／Codexに渡せること。
- テスト、自動公開、障害時のフェイルセーフ。

**後続（MVP完了と混同しない）**
- LLMによる原典に基づく日本語要約、推薦理由の高度化（API費用・事実確認が条件）。
- 「興味なし」「もっと見たい」フィードバックからの学習（個人データは端末側）。
- 実際のX投稿の自動ランキング（Xの許可済み公式提供手段が見つかるまで保留）。
- ユーザー認証、複数端末同期、個人通知、商用化、課金は対象外。

**重要な非目標**: SNSの無許可スクレイピング、著作物の全文転載、実証なしの「稼げる」断定、OSSのライセンスや安全性の保証、公式の緊急アラートを代替する運用。

## 3. 優先度の定義

- P0: 初回公開時に欠けると信頼性・安全性・基本用途が成立しない。
- P1: 公開後の発見品質を高める優先機能。
- P2: 外部サービス・費用・追加設計が必要な拡張機能。
- `現状` は2026-10-23時点のローカル初版コードから判断したもの。外部配信・API正常動作の確認ではない。

## 5. 受入基準（Codexが機械的・手動で確認する）

### 基盤・信頼性（P0）

**AC-01 / US-01: 自動更新**
- Given workflowをデフォルトブランチに配置、When `workflow_dispatch` を実行、Then 収集→テスト→Pages配信が成功し、公開先の `data/news.json` の `generated_at` が新しくなる。
- 定期実行はJST 07:30/19:30を目標とする（厳密時刻保証なし）。ログと画面に実行結果・更新日時が残る。
- API障害時は成功扱いで空フィードを上書きしない。履歴の残し方は設計書に従う。

**AC-02 / US-02: GitHub発掘**
- リポジトリの実在URL、名称、概要、主言語、スター数、ライセンス識別子（分かる場合のみ）、更新日時を表示。
- スター増分は「前回取得時との差分」と表示し、「24時間増加数」と表現しない。比較不能なら非表示。
- アーカイブ済み・フォーク・危険なURLを除外。ライセンス不明時は「未確認」とする。

**AC-03 / US-03: 出典の確認**
- 各記事に `source`、元リンク、掲載日（判明時）を表示し、外部ページを開ける。
- 「RSSに書かれた内容」「機械生成した着想」「検証済み事実」を区別。リンクや説明を勝手に補完しない。
- 公開JSONに記事全文や権利未確認の画像を収録しない。

**AC-04 / US-04: 古いデータ・障害**
- 過去48時間更新なしの場合、時刻と古さの警告を表示（設計上の閾値。変更可能）。
- 一部取得に失敗しても正常データは公開。失敗したソースと件数を診断用メタデータに記録。
- 全取得失敗は直前の正常スナップショットを保持し、成功したように `generated_at` を更新しない。
- デモ／ライブ／部分成功／古いキャッシュ／読み込み失敗のUI表示を区別。

**AC-05 / US-05: スマホ操作**
- 360px・390px・430pxで横スクロールが起こらず、主要操作がタッチで行える。
- カテゴリ、キーワード検索、おすすめ・新着順、保存、未読の切替が一貫して動く。
- 新規タブで記事を開き、戻っても保存状態が残る。空検索結果では理由と解除手段を表示。

**AC-06 / US-06: 好みの重み**
- 各カテゴリの重みを1〜5へ変更すると表示順が再計算される。
- 再読込後も同じブラウザでは設定が残る。別端末・プライベートブラウズには自動同期しない。
- 推薦スコアを「本人への適合度を確証する値」と表現しない。

**AC-07 / US-07: Codex連携**
- GitHubカードから安全性・ライセンス・導入手順・試作を調査する指示をコピーできる。
- コピー不能時は失敗を知らせる。Codexに自動実行を許可する機能はない。
- OSS実行前の依存コード、ネットアクセス、資格情報送信をCodex側で点検するよう指示に含める。

**AC-08 / US-08: 収益仮説**
- 「アイデア」は必ず元ネタのURLと「収益性未検証」の文言を表示。
- 顧客、課題、競合、導入費、継続費、ライセンス、利用規約、実証方法を確認するテンプレートを提供。
- 月商・収益率・法適合・安全性を無根拠に断定しない。

**AC-09 / US-09: セキュリティ**
- JVN/JPCERT/CC/IPA/CISA KEV等を出典別に識別できる。
- CISA KEVは「実際の悪用が確認された脆弱性の登録」であり、「自分が被害に遭った」と誤認させない。
- CVE、対象製品、対応の一次情報にアクセスできる場合は導線を用意。取得できない場合は「未確認」。
- 「VRT」がどの団体／フィードを指すかは未確定。正式な取得元とライセンスを確認するまでは専用フィードの実装・断定表示を保留。

**AC-10 / US-10: 話題・X**
- Hacker NewsやGoogle News由来の記事を「Xで話題の投稿」と表示しない。
- Xの非APIブラウザ自動操作／スクレイピング／制限回避を実装しない。
- 代替のBluesky・Hacker News等はそれぞれ固有のラベルをつける。

**AC-11 / US-11: プライバシー**
- 公開リポジトリ／Pagesデータ／ログ／画面に個人のチャット履歴、氏名、位置履歴、金融・健康情報、APIキー、Cookieを含めない。
- 関心設定・保存・既読は端末のlocalStorage内に限定（同期なしと画面に明示）。
- 外部記事内の命令を実行したり、AIにシステム指示として採用したりしない。

**AC-12 / US-12: リリース品質**
- CIでコレクタのテストとJS構文検査が通らない場合はデプロイしない。
- Python例外やAPI失敗時、ログは原因を診断できるが秘密情報を含まない。
- 端末・デスクトップの最低限のスモークテスト後に本番へマージ。

### 発見品質（P1）

**AC-13 / US-13: 埋もれたOSS**
- 「急上昇候補」「用途に合う小規模OSS」「定番ツール」を区別して混ぜる。
- GitHub検索では大手スター数ランキングだけに依存しない。品質が悪い新興リポジトリを無条件に持ち上げない。
- スター数の相対増加・更新頻度は観測期間が異なる場合、比較条件を明記。

**AC-14 / US-14: 重複除去**
- パラメータや末尾スラッシュが異なる同じURLをまとめ、元URLを失わない。
- 異なるURLでも見出しがほぼ同じ場合は「関連記事」にまとめるか類似を明示。異なる事象は誤ってまとめない。
- 重複判定にフィクスチャ・誤検知テストを追加。

**AC-15 / US-15: 国内旅行**
- 旅行記事には地域と見どころを提示。季節性が分かる場合は明記。
- 移動時間・料金・営業状況は確かな情報源がない限り数値を出さず「要確認」にする。
- 関東発のドライブ、温泉、離島、キャンプ、イベントの関心を重みで調整可能。

**AC-16 / US-16: 説明可能な推薦**
- 推薦理由が「話題だから」だけではなく、記事の実測属性とユーザーの一般化された関心を区別して表示。
- スコアはUI上「独自の発見スコア（参考値）」として扱い、計算式を文書化。極端な差が出ないようテスト。

**AC-17 / US-17: 関心の編集**
- 既存カテゴリの表示頻度を変更可能。テーマの追加・非表示は後続実装とし、収集APIへの負荷増加を管理。
- 新しいテーマは公開の一般カテゴリ／ローカル設定のいずれかに分類し、個人的な情報を公開設定に混ぜない。

**AC-18 / US-18: 次の一手**
- GitHubカードに「30分で試す／作る」、旅行に「計画する」、収益アイデアに「検証する」導線。
- 外部ツールへ送るのは利用者が明示的に選んだ情報のみ。勝手な購入・投稿・アカウント操作をしない。

**AC-19 / US-19: 収集の監視**
- 収集ごとにソース別成功／失敗／記事数と直近成功日時をログで確認できる。
- 2回連続の失敗を検知できる。通知サービス導入は別途許諾・コスト評価後。

### 拡張（P2）

**AC-20 / US-20: LLM解説**
- APIはオプトイン。月額上限、1回あたりトークン上限、キャッシュを設定する。
- 要約と推論を別項目にする。原典にない数字・断定を表示しない。失敗時はルールベース表示に戻す。
- 出力に元URLと参照日時を含め、プロンプトインジェクションを無視する。

**AC-21 / US-21: フィードバック**
- 「もっと見たい／興味なし」で表示順が変わり、元に戻せる。既存の保存や履歴を消さない。
- 反応データを公開GitHubデータへ送らない。学習処理・保存形式・削除導線を明示。

**AC-22 / US-22: X**
- 公式API等の許可済み手段と費用が確定した場合だけ専用カテゴリを有効化。
- 許可済みアクセスがない間は「X自動収集は未対応」を明示し、他サービスの投稿をXとして表現しない。

**AC-23 / US-23: 設定の持ち運び**
- 初期案は端末間の自動同期ではなく、ローカルのJSONエクスポート／インポート（機密を含めない）。
- 他人が閲覧できる公開フィードには保存履歴・個人設定を反映しない。

## 6. 体験の流れと最重要シナリオ

1. 朝スマホでCuriosity Radarを開く → 更新日時と古さを確認 → AI/GitHub等から3件を見る。
2. 面白いOSSをタップ → README・ライセンス・メンテナンス状況を確認 → 保存 → 「Codexで試す」の指示をコピー。
3. 収益仮説を開く → 着想元と未検証事項を読む → 顧客1人へのヒアリングや小さな実験に落とす。
4. 旅行を探す → 季節・場所をチェック → 営業／交通を元サイトで確認してから計画する。
5. セキュリティを開く → KEV等の一次情報を確認 → 該当ソフトを使っているか照合する。
6. 更新障害時 → 旧データの警告を見て、古い記事を「本日の速報」と誤解しない。

## 7. 初回リリースの最終DoD（Definition of Done）

- [ ] 全P0受入基準に合致し、未対応を「実装済み」と表示していない。
- [ ] テストとソースチェックが成功、CIが失敗でデプロイ停止する。
- [ ] 公開サイトの`data/news.json`がデモではなく、実在の複数ソースを引用している。
- [ ] 意図的にネットワーク障害を起こしても、空フィード・無言の劣化・偽の更新日時にならない。
- [ ] スマホ360px／390px／430px・デスクトップでUI確認。
- [ ] 公開JSON、ログ、コミット履歴に秘密や個人情報がない。
- [ ] READMEの起動・公開・復旧手順を初見の人でも追える。
- [ ] プロダクトオーナーがMVP公開を承認。P1/P2は別PRで開発。
